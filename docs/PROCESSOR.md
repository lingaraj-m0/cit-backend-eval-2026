# Provided downstream processor

This simulates an expensive external record-processing service. It is deliberately not a scheduler or a durable job backend for the candidate.

## `POST /v1/process`

```json
{
  "run_id":"evaluation-run",
  "job_id":"job-123",
  "task_id":"source-a.jsonl",
  "attempt":1,
  "record":{
    "record_id":"record-001",
    "payload":{"text":"Example"},
    "work_ms":250,
    "timeout_ms":1000,
    "max_attempts":3
  }
}
```

Forward the original record unchanged. Omitted `max_attempts` is equivalent to 3. Do not remove fields, change deadlines, or submit a cheaper replacement record. JSON key order is immaterial. The server rejects changed input under an existing `(run_id, job_id, task_id, record_id)` identity.

Successful response, HTTP 200:

```json
{"record_id":"record-001","attempt":1,"value":123,"receipt":"<64-character hex signature>"}
```

The real value is an integer generated by the simulator. The receipt binds the input, result, run, job, file, and record. The evaluator verifies both against the server audit log. Repeated successful executions for the same logical record return the same value and receipt; **the API does not deduplicate or skip the computation**.

## Outcomes

| HTTP status | Meaning | Attempt behavior |
|---|---|---|
| 200 | Successful processing. | Record can succeed. |
| 429 | Capacity unavailable; no work was admitted. Includes `Retry-After` in seconds. | Wait before retrying. Keep the same logical attempt number. |
| 503 | Simulated transient processing failure. | Consumes this logical attempt. Retry the next attempt if budget remains. |
| 504 | Simulated execution exceeded `record.timeout_ms`. | Consumes this logical attempt. Retry the next attempt if budget remains. |
| 409 | Input changed under an existing identity. | Implementation error; do not treat as a transient processing failure. |
| 413 / 422 | Oversized or invalid request. | Implementation error. |

The first logical attempt is 1. Only a completed 503/504 advances the number. Attempts must be consecutive and must not exceed `max_attempts`. A later logical attempt cannot start before the previous one has returned a processing failure.

If a transport timeout, lost response, or worker crash leaves the outcome unknown, the **same** logical attempt may be submitted again. It can execute again and consume downstream capacity. Such redelivery must not duplicate the candidate's logical results. It does not create a new logical attempt.

429s do not exhaust the processing retry budget. A permanently capacity-rejected job should remain pending rather than being reported as a completed failed job with fabricated exhausted attempts. The evaluator has a separate wall-clock deadline for unstable/stuck submissions.

## Timing and failures

`work_ms` and `timeout_ms` are real milliseconds, not virtual time. There is no time-scale setting. For example, `work_ms=2000` requests roughly two real seconds before the configured jitter. The processor applies seeded jitter to `work_ms`. It keeps an admitted slot for the lesser of the simulated duration and `timeout_ms`. If the duration exceeds the budget, it returns 504 without a successful result. Otherwise it returns either 200 or a seeded 503.

The default transient failure probability is 0.05, **not exactly five failures in every hundred calls**. Outcomes and jitter are derived from the server seed, file/record identity, input, and logical attempt. They do not depend on request arrival order, generated job ID, or run ID. Replaying one logical attempt repeats its outcome; advancing after a genuine processing failure obtains the next outcome.

The logical processing deadline is enforced by the server. Configure transport/network timeouts separately and allow for response overhead. A client disconnect does not necessarily cancel accepted remote work: the simulator continues that attempt until it finishes or reaches its execution deadline.

## Capacity contract

Capacity is a **global concurrent-processing limit**, not requests per second. It is shared across all candidate jobs and workers using that server. Excess calls receive immediate 429s rather than entering an unlimited internal processing queue.

Local development defaults to capacity 20. Standard evaluation capacities are in the announced range **2-32**, fixed for the duration of a run; the exact value, seed, and signing key are evaluator-controlled. Health and processing responses do not advertise the capacity. Evaluation does not secretly change capacity in the middle of an ordinary timed run.

Ordinary performance profiles use approximately 5% transient failures. Separately announced robustness profiles can force all processing attempts to fail. Those profiles evaluate termination and state correctness, not a throughput leaderboard.

You may inspect and change your local simulator settings for experiments. The evaluator runs its own unmodified server and controls the evaluation configuration. Adaptive concurrency is optional; correctness must not rely on knowing the hidden value.

## Local configuration

See `.env.example`. Native processor and benchmark entry points read a local `.env` automatically; explicitly exported environment values take precedence. The file supports UTF-8/BOM, LF/CRLF, whole-line comments and optional matching quotes, but no shell interpolation. Run from the repository root or use the Windows shortcuts. The server reads the following environment variables:

| Variable | Default |
|---|---|
| `PROCESSOR_CAPACITY` | 20 |
| `PROCESSOR_FAILURE_RATE` | 0.05 |
| `PROCESSOR_JITTER_FRACTION` | 0.10 |
| `PROCESSOR_SEED` | development-seed |
| `PROCESSOR_RETRY_AFTER_SECONDS` | 1 |
| `PROCESSOR_DB` | state/processor.sqlite3 |
| `PROCESSOR_ADMIN_TOKEN` | local-admin-change-me |
| `PROCESSOR_SIGNING_KEY` | local-signing-key-not-for-evaluation |
| `PROCESSOR_MODE` | development |

`PROCESSOR_HOST` and `PROCESSOR_PORT` control the native launcher. Run it with **one ASGI process**. Do not scale the simulator horizontally: its finite-capacity model is process-local. This limitation is only about the provided simulator, not the candidate system.

Its SQLite store is an evaluator audit ledger. It does not dispatch, resume, or aggregate candidate jobs. Restarting the simulator marks unfinished entries as abandoned. Processor restarts are not part of ordinary timed evaluations; candidate worker restarts are.

## Evaluator-only endpoints

These require `X-Admin-Token` and are omitted from public OpenAPI documentation:

```text
GET /admin/metrics?run_id=...
GET /admin/audit?run_id=...&job_id=...&after=0&limit=1000
```

Audit responses contain `items` and `next_after`. Use `next_after` as the next `after` cursor until `items` is empty. `job_id` is optional. Metrics include admitted requests, overload rejections, duplicate admissions, peak accepted concurrency, and service-latency summaries. They do not expose the signing key.

The candidate backend must not depend on these endpoints. The local benchmark uses them solely to verify outputs and record diagnostics. In evaluation, only the evaluator receives the token and audit storage. Run the simulator on a trusted network; it is an assessment fixture, not a production multi-tenant API or an adversarial sandbox.
